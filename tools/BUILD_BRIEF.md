## 2. 什麼時候才需要自己去翻 war3map.j

**多數情況不需要。** 卷宗已經把「這個技能 ID 出現的分支 + 它呼叫的回呼」抽出來了。

只有這幾種情況才值得自己解 JASS（解到你自己的暫存目錄，不要寫進 repo）：

- 卷宗某個技能標著「JASS 裡沒有對應實作」，而你需要確認它到底有沒有被別處引用
- 你要追**道具**的行為（卷宗只涵蓋英雄技能；道具邏輯在
  `Trig_ItemAttacksFromHero_Actions` / `Trig_UseSkillsEndcast_Actions` /
  `Trig_ItemKills_Actions` 這幾支裡）
- 你要確認召喚物繼承了什麼（grep 召喚物的 unit ID）
- 你懷疑卷宗的程式碼被 `MAXCODE` 截斷了（每個技能最多 260 行）

```bash
python -c "
import sys,io,json; sys.path.insert(0,'tools'); import mpq
V=json.load(io.open('tools/version.json',encoding='utf-8'))
io.open('war3map.j','w',encoding='utf-8').write(
    mpq.MPQ(V['map_file']).read('war3map.j').decode('utf-8','replace'))"
```

那份檔案有 66226 行、2.1 MB —— **不要整份讀**，只 grep 你要的東西。
`udg_ItemBonusDMG[玩家編號]` 是**技能強度**，
`LoadReal(hash,<單位>,18)` 是**裝備技能威力**。

## 3. 已驗證的核心機制

**加法為主。** 所有百分比修正都是加進同一個係數，沒有乘法疊乘。
唯一的兩層結構是「技能強度 → 技能傷害」與「裝備技能威力 → 道具觸發傷害」，
兩者作用在不同的東西上，不會互乘。

**狀態傷害的算法**（以點燃為例，`BurnUnit` / `Burn_Dmg`）：

```
總傷害 = 底值 × cof × (跳數 / 16)
cof   = 1.00
      + 你的「點燃傷害 +X%」            （key 27 實數槽）
      + 0.50  帶零時迷子 I086 且自己有「抵抗點燃」旗標
      + 0.35  目標冰凍 且 自己帶石英法杖 gvsm／寒冰之球 I00S
      − 目標的點燃抗性                  （key 47；電擊會讓它 −1.00）
      下限 0.20
跳數  = 16，目標有「易燃」時變 32（總傷害翻倍）
機率  = 底值 × 1.5（目標有易燃）× 1.5（自己帶幸運馬蹄鐵 I09G）  ← 相乘
```

**四個關鍵陷阱**：

1. **流血／疾病的「+X% 傷害」是壞的。** `Bleed_Dmg` 第 2069 行、`Disease_Dmg`
   第 2267 行把加成寫進 `dmg_cof`，但傷害用的是更早複製出來的 `cof`。
   只有點燃是對的。所以不要為了「+X% 流血傷害」去配裝。
2. **易燃讓點燃跳數 16→32，總傷害翻倍**（遊戲說明寫 +50%）。
3. **「抵抗X」是二元旗標，跟「+X% 抗性」是兩回事。** 零時迷子 I086 檢查的是
   旗標，帶 +75% 點燃抗性但沒有「抵抗點燃」的裝備完全觸發不了它。
4. **電擊把四種狀態抗性各 −1.00**，等於所有狀態係數 +1.00，而且沒有裝備能擋。

**穿透（pen，hash key 16）不是護甲穿透。**
`Trig_HeroTakeDamage_Actions` 第 20057 行起：每一次傷害事件之後，額外再打一段
`ATTACK_TYPE_CHAOS / DAMAGE_TYPE_UNIVERSAL` 的傷害，數值就是攻擊者的穿透值，
不受任何減傷影響，也跟目標護甲無關。目標冰凍時 ×1.5，對建築完全不生效。
狀態跳傷因為外面包了 `DisableTrigger(gg_trg_HeroTakeDamage)`，不會附帶穿透。

所以穿透的價值只看**你製造多少次傷害事件**：多段技能、多目標技能、高攻速的
英雄拿穿透特別划算，單發大招的英雄拿了幾乎沒感覺。

**召喚物不繼承主人的裝備。** （由死靈法師那一輪查證，適用於全部召喚師）
`Trig_ItemAttacksFromHero_Conditions` 要求 `IsUnitType(GetAttacker(), UNIT_TYPE_HERO)`，
`Trig_ItemKills_Actions` 讀的是擊殺者 handle 上的道具計數，
`Trig_HeroTakeDamage_Actions` 的 DefCof 全部讀攻擊者 handle 上的 key 3/5/6/9/40/41 ——
召喚物身上什麼都沒存，所以**裝備觸發、裝備施加的狀態、「造成傷害 +X%」對召喚物全部無效**。
週期性道具效果（`Trig_EveryNsecSkills_Actions`）也只跑 `udg_AllHeroes`。

召喚物**吃得到**的只有三種：主人技能公式裡明寫的屬性（最大生命／智力／技能強度）、
原生光環（`ACav`/`SCae`/`Acht` 之類，buff ID 不同才會疊加）、
以及背包裡沒用掉的吸收器 `I089` —— 但那個 +5 護甲**不是通則**，是在 12 個
召喚處各自寫死的（死靈法師的骷髏與法師、幽魂、以及另外幾隻英雄的召喚物）。
建築師的塔就沒有。要用之前先 grep `UnitHasItemOfType(u,'I089')` 確認你的英雄在不在裡面。

**9 個「施法時觸發」道具的內部冷卻沒生效**，每次施法都觸發：
獅子星座 `ofro`、水晶法杖 `I06X`、海克斯科技 `shtm`、平紋褲 `I01T`、
侍僧之褲 `hcun`、術士之褲 `clfm`、大法師之褲 `odef`、林后之冠 `oslo`、
治癒之球 `glsk`。連續施法的英雄拿這些特別划算。
（大法師之褲的回復量實作用的是力量，不是說明寫的智力。）

**狀態堆疊會被靜默丟掉。** `BurnUnit` 重用過期槽位時把堆疊數量寫成槽位編號，
`Burn_Dmg` 只跑到那個數字，編號更大的存活堆疊永遠不再結算（流血／疾病同樣）。
所以「對同一目標高頻疊狀態」的實際收益會低於理論值，估算時要保守。

**皮膚會換技能。** 41 個皮膚裡有 25 個的英雄技能跟本體不一樣。
設計配裝前先看 `h['skins']` 裡有沒有 `add`/`rm` —— 如果你的英雄有這種皮膚，
配裝要說清楚是給本體還是給皮膚形態用的。

**苦難面具 I068** 反彈的是**原始傷害＋穿透**的 20%，不受雙方減傷影響，
沒有內冷，但只對敵方英雄生效。

**有兩個「永久累加技能強度」的來源，長局會滾雪球：**
`udg_ItemBonusDMG[玩家]` 這個全域變數只在開場初始化一次，之後靠裝備穿脫加減。
有兩個東西會**永久**往上加、死亡不歸零、沒有上限：
- **吸收加速器 `I0AZ`** —— 每次擊殺 +1（條件是 `GetUnitLevel(死者) != 0`，0 級雜兵不算）
- **樹人長者的魔力潮汐** —— 每次施放對**目標玩家**永久 +（3 + 2×等級），滿級 13
估長局價值時要把這兩個算進去；短局則幾乎沒有意義。

**建築（`UNIT_TYPE_STRUCTURE`）與機械單位的狀態抵抗不是一致的：**
冰凍、流血、疾病、虛弱、詛咒、易傷、電擊、魅惑、切割、詛咒審判這 10 種
`chanse=0.`（完全免疫）；但**點燃與易燃只是 `chanse*0.50`**，不是免疫。
敵方的穿透打不到建築；建築打有反傷的目標時反傷 ×0.5。

**`SetUnitLife` 改的是生命「上限」，不是當前血量。** 這個已經被誤讀兩次，
兩次都差點被當成「說明寫 +15、實際是全額回血」的大 bug 回報出去：

```jass
function SetUnitLife takes unit c,integer hp returns nothing
    set hp=R2I(I2R(hp)-(GetUnitState((c),UNIT_STATE_MAX_LIFE)))   // 先轉成「差值」
    …  UnitAddAbility(c,'ah00') / SetUnitAbilityLevel(…)          // 用 ah00 加減
```

`ah00` 的原型是 `AIl2`（Item Life Bonus），`Ilif` 欄位是 ±1/2/5/…/2000 的
**生命上限**加成。所以 `SetUnitLife(u, 最大生命 + 15)` ＝ 上限永久 +15，
而不是把血補滿。同理 `GetUnitLife` 讀的 key 37 只是「最後一次呼叫的差值」，
不是生命值（見 地圖問題回報 A-9）。

**力量系才會碰到的四件事**（前 23 隻智力／敏捷英雄都沒踩到）：

- **反傷是一條獨立管線**，不在 `_engine.md` 的傷害管線那 697 行裡 ——
  在 `Trig_UAttacks_Actions`，掛的是 `EVENT_PLAYER_UNIT_ATTACKED`
  （**起手動作**就結算，打不打得到無所謂），走 `CHAOS/UNIVERSAL`、
  外面包 `DisableTrigger`。所以它不吃對方護甲、不吃護甲類型、不經 DefCof、
  也跟對方攻擊力無關 —— **縮放來源是「被幾隻打 × 對方攻速」**，
  跟其他英雄的「你打幾次」正好相反。公式：`key17 × (1 + key19)`。
- **格擋**是另一條，走原生能力、不在腳本裡，卷宗抽不到，要從道具說明讀。
- **護甲類型倍率這時才真的重要**：英雄護甲對魔法／穿刺 ×0.60、攻城 ×0.50，
  只有普通與混亂是 1.00。法師在意「怎麼把傷害打出去」，坦克在意
  「進來的是哪一種攻擊類型」。
- **DefCof 的「減項」是力量系才用得到的半邊**：黃金鎧甲（缺血越多減越多）、
  帝王鎧甲、救贖腰帶、英勇頭盔…… 它們彼此相加，但跟護甲相乘。

**沒有任何裝備能縮短英雄技能的冷卻。** `key 1`（裝備技能冷卻）只經過
`StartModCooldown(u_Id, 道具ID, CD)`，參數是**道具 ID** —— 那個屬性只作用在
道具觸發的內部冷卻上。不用再為每隻英雄試一次。

**技能不一定來自腳本。** 只 grep `war3map.j` 找不到 `UnitAddAbility` 就斷定
「這個技能拿不到／是死碼」已經誤判過兩次 —— 很多技能是寫在物件資料的
`uabi`（固有）或 `uhab`（可學）裡，單位一被創造就有。例如皇家守衛的
`A0Y5` 聖物守衛就在 `Hapm.uabi` 裡。判斷來源要一併看 `war3map.w3u`：

```bash
python -c "
import sys,io,json; sys.path.insert(0,'tools'); import mpq,w3obj
V=json.load(io.open('tools/version.json',encoding='utf-8'))
U=w3obj.parse(mpq.MPQ(V['map_file']).read('war3map.w3u'))
u=U['Hapm']; print(u.get('uabi'), u.get('uhab'))"
```

**這些常數地圖沒有覆寫，走魔獸預設**（`war3mapMisc.txt` 只改了
`AgiDefenseBase/-Bonus`、`AgiAttackSpeedBonus` 與八張護甲倍率表）：
25 生命／點力量、15 法力／點智力、0.06 護甲減傷係數。

## 4. 配裝規則（硬性）

- **6 個正常欄位**，另外兩個不佔格的額外欄位：
  - `s1` = 吸收器（特殊 lv.1）—— 自己挑一件
  - `s2` = 祕密寶盒（特殊 lv.2）—— 隨機生成，所以只能算「期望值」
- 同一件神器最多 1 個（鐵匠可以複製其中 1 件，所以最多 1 件能出現 2 次）
- **耳環最多 1 件** —— `TryTakeEarringsSlot`；星界耳環 I00E、翡翠耳環 I00F、
  黃金耳環 I00O、紅寶石耳環 I00P、藍寶石耳環 I00Q
- **乘算器最多 1 件** —— `TryTakeMultiplierSlot`（違反時遊戲會跳錯誤訊息並把
  裝備退回地上）：朱砂護符 ckng、優雅吊墜 tfar、大奶酪 oven、低語觸手 kysn、
  靈魂之石 jpnt、黑暗水晶 moon、守護者護肩 I0A8、耶夢加得之戒 I01P、
  洪流項鍊 I00B、**洞察之戒 I078**（走另一段程式碼但佔同一個 player key 13）。
  封閉心智頭盔 iwbr 走同一個處理器但**不佔格**，可以跟真正的乘算器同時帶。
- 每套最多 1 件 特殊 lv.5+

**取得難度篩選**（實務考量，不是遊戲規則）：排除 新年／復活節／萬聖節／儀式
（要盜賊）、完美（要鐵匠）、特殊 lv.5++（幾乎抽不到）。

**例外：鐵匠 `H00P` 自己的配裝可以用「完美」道具**，因為那正是他做出來的 ——
「無雙鐵匠 `A09J`」把四件聖物鍛成完美（瓊漿玉液→返老還童藥劑、
不詳之盾→復仇之盾、信仰之錘→科技之錘、穿刺長矛→隕星長矛），一場一次。
同一個技能的另一條分支可以複製一件神器（也是一場一次，原件不移除）。
`check_build.py` 有這條例外，用 `--hero H00P` 或 `--file`（會自動依英雄判斷）。

用 `python tools/check_build.py --file 你的檔案.json` 驗證，
**每一套都要通過才算完成**。

## 5. 輸出格式

寫成 JSON，格式跟 `tools/hero_builds.json` 一致：

```json
{
  "英雄ID": [
    {
      "id": "bishop-heal",
      "c": "#7E8CE0",
      "talent": "A0XX",
      "n": ["中文名", "English name", "Русское название"],
      "key": ["一句話重點（中）", "(en)", "(ru)"],
      "why": ["為什麼有效（中，200-400 字，要有具體數字與程式碼依據）", "(en)", "(ru)"],
      "items": ["I00E", "sor5", "kpin", "I067", "I086", "I06A"],
      "bonus": {"s1": "oli2", "s2": "I0AV"}
    }
  ]
}
```

- `talent` 只在配裝綁定特定天賦時填，否則整個欄位省略
- `c` 是配裝卡片的主色，挑一個跟配裝調性相符的十六進位色
- `n` / `key` / `why` 三語都要，俄文可以短一點但要正確
- `why` 要寫出**為什麼**，而且要有數字。不要寫「這件裝備很強」這種空話；
  要寫「均衡者之眼是 50 + 技能強度×0.20、22 跳，等於技能強度×4.4」

## 6. 配裝要有分工

每隻英雄給 3～4 套，彼此要**真的不一樣**，不要只是換一兩件：

- **高輸出型** —— 把這隻英雄最好的傷害係數推到極限
- **穩定型** —— 犧牲一部分輸出換生存或續戰，要說清楚換了多少
- **創意型** —— 利用一個不明顯的機制（門檻、旗標、反直覺的條件），
  這一套最有價值，但**必須有程式碼依據**
- **平價型**（選配）—— 一萬金以內、中期就能湊齊

不限於輸出。治療、召喚、輔助、坦克、法力壓制、金錢收益都可以是主軸，
只要說得出數字。

## 7. 誠實原則

- 沒有從程式碼確認的事情，就寫「無法從地圖資料確認」，不要猜
- 發現說明與實作不符，回報出來（會併進 `地圖問題回報.md`）
- 數字要能重現，必要時附上你算的方式
